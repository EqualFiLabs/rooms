# Rehearsal preparation

Production terms remain unset in the example launch-input file. The target is Robinhood Testnet, chain 46630, as specified by the [official connection documentation](https://docs.robinhood.com/chain/connecting/). Local Osaka execution does not establish that a target client supports every generated opcode. A separately collected target-client execution receipt is required by preflight.

`DeployRooms.prepare` locally assembles fresh code and activation calldata without a broadcaster or signing material. Supply explicit initializer inputs and a positive expected external timelock delay. The Diamond constructor assigns authority directly to that timelock. Its complete first application cut and initialization execute together after the timelock delay. No temporary deployer authority or handover is used. Local addresses and calldata describe that simulation only; future deployment must regenerate them for its actual creations and verify runtime identities before scheduling activation. The script does not finalize selectors.

The assembly test executes an OpenZeppelin timelock with concrete local proposers, executors, administrators and delay; rejects direct cuts and early execution; installs every release selector; buys through the resulting Diamond; and exercises timelock governance after local finalization. Fixture addresses and delays are not production inputs.

`python3 tools/build_manifest.py candidate-manifest.json` binds compiler/dependencies, source SHA-256, runtime Keccak hashes, complete selector ownership and namespace/ordered-struct schema digests. Schema digests are review aids, not an automatic storage compatibility proof. A changed ordered type or namespace requires explicit compatibility review.

`python3 tools/preflight.py PLAN MANIFEST OBSERVATIONS` validates supplied block-pinned read observations, candidate binding, code identities, initialized selector ownership, external authority/delay/role inventory, asset attestations, initial 50/20/30 economics, Router readiness and a future uncached Registry target probe. It never obtains observations itself and cannot authenticate a JSON file or infer current chain state. Role inventory requires complete grant/revoke history review because ordinary TimelockController does not enumerate members; listed `hasRole` checks alone cannot exclude unknown members. Open execution through the zero address is intentionally rejected by this release policy. Asset behavior and canonical identity require issuer/source review, not a boolean inferred from ERC-20 metadata. Integration code hashes must be independently tied to the reviewed dependencies and actual deployment configuration before these files are supplied.

Current live state: **prepared but unexecuted**. No deployment, signing, broadcast, live role confirmation, target-client execution or irreversible finalization is performed. The future live sequence must be separately authorized and block-pinned. A fresh Diamond must use approved assets and verified Registry/Router, mixed epochs, concurrent configurations/assets, both cutoffs, actual future Quicknet proof and cache reuse, claims and revenues, a failed delivery and retry, then separately authorized progressive finalization. Do not retarget to obtain a desired winning room. Empty outcomes must arise honestly; deterministic local tests cover branches not obtained live. Thirty-day expiry is locally time-controlled coverage, not a same-day live observation.

Run `python3 tools/rehearse.py --output rehearsal-result.json` from the checkout. It prepares the pinned Registry test source, builds the candidate, executes eight named actual-Diamond suites and rejects missing, empty, failed or skipped suites. The local exercise passed 29 tests, including real Quicknet/Router integration, both cutoffs, concurrent assets/configurations, repeated empty rollover, claims/expiry, revenue retry and timelock activation. Its output binds the candidate manifest and labels every result local, with signing and broadcasting false. No live mode is implemented.
